# 이메일 로그인과 계정 관리

실제 `/` 화면에서 이메일·비밀번호로 가입하거나 로그인합니다. 외부 인증 키나 메일 발송 서버 없이 동작하며 카카오 로그인 버튼은 표시하지 않습니다. 기존 카카오 API 경로는 호환성을 위해 유지합니다. 시니어의 `/w/<token>` 대화방은 기존과 같이 로그인 없이 공유 토큰으로 접근합니다.

## 이용 흐름

1. 첫 화면에서 회원가입을 선택하고 이름·이메일·비밀번호·비밀번호 확인을 입력합니다.
2. 가입 후 로그인 쿠키가 발급되며, 아직 완료하지 않은 동의·대상자·목소리·사진 단계로 연결됩니다.
3. 이후에는 이메일과 비밀번호로 접속합니다. 이메일 앞뒤 공백과 대소문자는 구별하지 않습니다.
4. 설정(`/settings`)에서 이메일을 확인하고 비밀번호를 바꾸거나 로그아웃합니다.
5. 비밀번호를 변경하면 모든 기존 세션을 폐기하고 현재 브라우저에 새 세션을 발급합니다.

로그인 이전에 접근하려던 보호 화면은 `next` 쿼리에 담습니다. 온보딩이 완료된 계정만 해당 화면으로 돌아가며 외부 주소·공유 링크·API 주소로는 돌아가지 않습니다. 보호 화면은 창에 다시 돌아왔을 때 로그인 상태를 재확인합니다.

이메일 주소 소유 확인, 비밀번호를 잊었을 때 이메일로 재설정, 다중 인증은 현재 제공하지 않습니다. 이메일 발송·인증이 완료됐다는 표시나 작동하지 않는 복구 버튼을 두지 않습니다.

## 입력과 API

| 경로 | 요청 본문 | 동작 |
|---|---|---|
| `GET /api/auth/config` | 없음 | 이메일 로그인 활성화, 개발 로그인 표시 여부, 비밀번호 길이 반환 |
| `POST /api/auth/register` | `{name,email,password}` | 계정 생성과 로그인 |
| `POST /api/auth/login` | `{email,password}` | 기존 계정 로그인 |
| `POST /api/auth/logout` | 없음 | 현재 서버 세션 폐기와 쿠키 삭제 |
| `POST /api/auth/credentials` | `{email,password}` | 로그인한 기존 개발용·카카오 계정에 이메일 연결 |
| `POST /api/auth/password` | `{current_password,new_password}` | 현재 비밀번호 확인 후 변경·전체 세션 교체 |
| `GET /api/me` | 없음 | 현재 사용자·이메일·로그인 방식·서비스 준비 상태 |

가입·로그인·이메일 연결·비밀번호 변경 성공 응답은 `{ok:true,user:{id,name,email,kakao,auth_method,has_password},next}`입니다. 로그아웃은 `{ok:true}`를 반환합니다. `next`는 `/onboarding/consent`, `/onboarding/parent`, `/onboarding/voice`, `/onboarding/photo`, `/home` 중 현재 계정 상태에 맞는 값입니다.

- 이름은 앞뒤 공백 제거 후 1~50자입니다.
- 이메일은 최대 254자이고 ASCII 이메일 형식을 검사합니다. 국제화 이메일 주소는 지원하지 않습니다. 공백 제거·소문자 변환한 이메일에 DB 고유 제약을 적용합니다.
- 테스트 단계의 새 비밀번호 조건은 Unicode 문자 기준 4자 이상입니다. 문자 조합과 최대 길이 제한은 없으며 공백도 그대로 보존합니다. 확인 입력은 화면에서 검사하고 최소 길이는 서버에서도 검사합니다.
- 같은 이메일로 동시 가입을 시도해도 한 계정만 생성되며 실패한 가입의 빈 사용자 행은 남기지 않습니다.
- 잘못된 로그인은 이메일 존재 여부와 관계없이 같은 401 응답을 반환합니다. 인증 입력 검증 오류에는 제출한 비밀번호를 포함하지 않습니다.
- 인증 응답과 `/api/me`는 `private, no-store`로 반환합니다.

## 비밀번호와 서버 세션

비밀번호는 사용자별 16바이트 무작위 salt와 PBKDF2-HMAC-SHA256 600,000회로 해시합니다. 저장 형식에 알고리즘과 반복 횟수를 포함하며, 비교에는 `hmac.compare_digest`를 사용합니다. 없는 이메일도 더미 해시를 확인해 비밀번호 확인 비용이 빠지지 않도록 처리합니다. 구현 기준은 [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)입니다.

로그인마다 32바이트 무작위 세션 식별자를 생성하고 DB에는 식별자의 SHA-256 해시만 저장합니다. 브라우저 쿠키에는 `{uid,sid,exp}`를 HMAC으로 서명한 값을 넣습니다. 서명·자료형·만료 시각을 검사한 뒤 DB의 사용자·식별자·만료·폐기 상태를 다시 확인합니다. 쿠키만 복사해도 서버에서 폐기한 세션은 재사용할 수 없습니다.

쿠키는 `HttpOnly`, `SameSite=Lax`, `Path=/`이며 기본 수명은 30일입니다. `PUBLIC_BASE_URL`이 HTTPS이면 `Secure`도 적용합니다. 로그아웃은 현재 세션을 폐기합니다. 비밀번호 변경과 기존 계정의 이메일 연결은 해당 사용자의 모든 기존 세션을 폐기하고 현재 브라우저만 새로 로그인시킵니다.

비밀번호 확인을 마친 로그인 요청과 비밀번호 변경이 겹쳐도, 사용자별 잠금 후 최신 비밀번호 해시를 재확인합니다. 변경 전에 확인한 이전 비밀번호로 변경 후 새 세션이 발급되지 않도록 합니다. SQLite는 사용자 행의 무해한 UPDATE로 쓰기 잠금을 획득하고 다른 DB에서는 행 잠금을 사용합니다.

새 서버 세션 구조에는 기존 `{uid,exp}` 쿠키를 승계하지 않습니다. 업데이트 직후 기존 사용자는 한 번 다시 로그인해야 하며, 계정과 영상·대화 데이터는 유지됩니다.

## 요청 출처와 시도 제한

API의 POST·PUT·PATCH·DELETE는 브라우저 `Origin`을 서버 주소 또는 `PUBLIC_BASE_URL`과 비교하고 `Sec-Fetch-Site: cross-site`도 차단합니다. 임의 `X-Forwarded-Host`를 출처 검증에 사용하지 않습니다. 브라우저 헤더를 보내지 않는 CLI·테스트 클라이언트는 사용할 수 있습니다. 출처 검사는 인증·공유 토큰 검사를 대신하지 않습니다.

DB 기반 15분 고정 구간 카운터를 사용해 여러 API 작업자에서도 제한이 공유됩니다.

| 범위 | 제한 |
|---|---|
| 로그인 / 클라이언트 IP | 30회 / 15분 |
| 로그인 / 정규화된 이메일 | 10회 / 15분 |
| 가입 / 클라이언트 IP | 10회 / 15분 |
| 이메일 연결·비밀번호 변경·개발 로그인 | 각 경로별 IP 10회 / 15분 |

제한을 넘으면 429와 `Retry-After: 900`을 반환합니다. 원문 이메일과 IP 대신 범위를 해시한 키를 저장하고 만료 카운터를 정리합니다. 애플리케이션이 임의 `X-Forwarded-For`를 직접 신뢰하지 않으며 ASGI가 제공한 클라이언트 주소를 사용합니다. 프록시 뒤에서는 Uvicorn·프록시의 신뢰할 프록시 범위를 정확히 설정해야 합니다. 모든 사용자가 프록시 IP 하나로 전달되면 IP 제한도 공유됩니다. 외부에서 직접 접근 가능한 서버에서 모든 전달 헤더를 신뢰하도록 설정하지 마세요.

## 기존 개발 계정 연결과 배포

개발용 이름 로그인은 `DEV_LOGIN=false`가 기본입니다. 카카오 키가 비어 있어도 자동으로 켜지지 않습니다. 기존 개발 계정의 데이터를 이메일 계정으로 이어 쓰려면 신뢰할 수 있는 로컬 환경에서만 `DEV_LOGIN=true`로 실행하고 기존 이름으로 로그인합니다. 설정에서 이메일·비밀번호를 연결한 뒤 `DEV_LOGIN=false`로 되돌립니다. 연결이 끝난 계정은 개발 로그인을 켜도 이름만으로 접속할 수 없습니다. 연결 작업은 기존 사용자 ID, 대상자, 영상, 답글, 공유 토큰을 바꾸지 않습니다.

시작 시 기존 DB에 `account_credentials`, `auth_sessions`, `auth_rate_limits` 테이블을 추가합니다. 사용자 테이블의 이메일 열을 임시로 덧붙이거나 기존 계정을 삭제하지 않습니다. 실제 사용자 데이터로 DB 초기화 명령을 실행할 필요가 없습니다.

운영에서는 HTTPS와 고정된 긴 `SESSION_SECRET`을 지정하고 모든 API 인스턴스에 같은 값을 사용합니다. 로컬에서 시크릿을 생략하면 기존 설정과 같이 데이터 폴더의 `.session_secret`을 사용합니다. 시크릿을 교체하면 기존 로그인 쿠키를 다시 사용할 수 없습니다.

## 검증

```powershell
conda activate ai-video-letter
python -m unittest discover -s backend/tests -v
npm run lint
npm run build
```

인증 테스트와 기존 대화 테스트는 공통 임시 SQLite·미디어 경로를 사용하며 실제 DB·환경 파일을 수정하지 않습니다. 이메일 정규화·중복 및 동시 가입, 비밀번호 저장·검증, 쿠키 위변조·자료형·만료, 로그아웃 재사용 차단, 모든 기존 세션 폐기, 비밀번호 변경 중 이전 비밀번호 로그인 차단, 기존 계정 데이터 유지, 출처 검사, 시도 제한, 이전 DB 호환을 확인합니다.
